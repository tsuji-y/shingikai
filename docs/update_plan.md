元の案との違いは 7 節にまとめた。決めていただく事項は 8 節にある。

## 1. 目的と範囲

既存のデータベース（`data/mod/`）を 1 日 1 回、最新に保つ。新しいシステムは作らず、既存のスクリプトと表に自動化を足す。

対象：

- `/j/policy/agenda/meeting/` 配下の HTML すべて（現在 123 ページ。アーカイブ区分の 46 ページを含む）
- そこからリンクされている www.mod.go.jp 上の PDF（現在 421 件）
- RSS 2 本（`update.xml`、`news.xml`）

対象外：

- 国立国会図書館のアーカイブ（WARP）上の本体。`robots.txt` が禁じているので取得しない。URL だけ記録する
- 外部サイト（内閣官房など）。URL だけ記録する
- PDF の URL を推測して探すこと

検知するイベント：

1. 会議体の追加・名称変更・一覧からの削除
2. 会議（回次）の追加
3. 資料・議事録・議事要旨の追加（後日の追記を含む）
4. 資料の差し替え（同じ URL のまま内容が変わる）
5. 資料の WARP への移動
6. 委員名簿・概要の変更
7. ページの追加・消失

## 3. 構成

### 3.1 実行基盤

Phase 0 の結果で決める。

| 処理 | 実行場所 |
|---|---|
| RSS の取得（`poll_rss.py`） | GitHub のランナー。クラウドからも取得でき、端末が閉じていても更新ログが欠けない |
| HTML のチェック、取り込み、PDF の取得、Gemini | GitHub のランナーで HTML が安定して取れるなら、そこで動かす。403 なら、この端末で動かす |

この端末で動かす場合の方法は 2 つある。

- **セルフホストランナー**：ワークフローは GitHub Actions のまま、実行だけこの端末で行う。端末が閉じている間のジョブは待機し、端末が開いたときに動く（待機の上限は 24 時間。Phase 0 で確認する）。
- **Windows のタスクスケジューラ**：ランナーを入れられない場合の代替。逃した回を次に端末が開いたときに実行する設定にする。

採用しないもの：

- Cloud Run Jobs と Dockerfile。拒否の原因が「海外 IP」だという確認がなく、東京のデータセンターなら通るという保証がない。
- Playwright などのブラウザ自動操作。対象ページは静的な HTML で、描画のためには要らない。使い道がボット検証の通過になり、README の方針に反する。

### 3.2 日次の流れ

1. **更新チェック**：台帳（`raw/mod/pages.csv`）の全ページを、`If-Modified-Since` 付きで 1 件ずつ取得する。
2. **変更ページの保存**：変更があったページを `raw/mod/pages/` に保存し、台帳を更新する。
3. **新しいページの取得**：変更ページのリンクのうち、`/j/policy/agenda/meeting/` 配下で台帳にない HTML を取得する。1 回の実行で取得する新規ページは 30 件までとする。
4. **表の作り直し**：`build_db.py`。
5. **資料の取得**：`fetch_files.py`（台帳にない PDF だけ）→ `extract_text.py` → `build_db.py`。
6. **イベントの記録**：作り直す前後の表をキーで比べ、`events.csv` に追記する（3.7 節）。
7. **回帰の検査**（3.8 節）。通らなければ commit しない。
8. **commit と push、通知**：変更があった日だけ。
9. **Gemini の処理**（3.9 節）：別のステップ、別の commit にする。Gemini が失敗しても、8 までの更新は失われない。

週に 1 回、取得済みの PDF 全件を条件付き取得で照合し、差し替えを検知する（約 420 件、2 秒間隔で 15 分ほど）。

### 3.3 変更検知の規則

| 応答 | 扱い |
|---|---|
| 304 | 変更なし |
| 200 | 差し込みスクリプトを除いた本文のハッシュを台帳と比べる。同じなら変更なし（`last_modified` だけ更新）。違えば変更あり |
| 404、410 | 消失の候補。2 回続けて同じ結果なら消失として記録する。保存済みのファイルは消さない |
| 403、429 | その場で止める（3.4 節） |

- 生のバイト列のハッシュ（既存の `sha256` 列）は、変更検知に使わない。
- 台帳に `content_sha256` 列を足す。`cdn-cgi/challenge-platform` を含む `<script>…</script>` を除いてから計算する。既存の 123 ページ分は、保存済みのファイルから計算して埋める。
- 保存するファイルは、これまでどおり取得したバイト列のままとする。

### 3.4 止める規則と失敗の扱い

- 403・429 が返ったら、その場で止める。リトライしない。その日はもう取りに行かない。
- 止まった回は「変更なし」ではなく「未確認」として扱い、ジョブを失敗にする。
- User-Agent を変えて通そうとしない。ブラウザに見せかけない。
- リトライするのは、タイムアウトと 5xx だけ（間隔を広げながら最大 3 回）。
- 取得できなかったページを「消失」と判定しない。
- チェックできたページが 0 件なら失敗にする。

Python で取得できなくなった場合は、ブラウザ経由（`fetch_in_browser.js` と `ingest_pages.py`）に切り替える。これは手作業か、Claude in Chrome で行う。

### 3.5 WARP への移動

防衛省のページは、古い資料のリンクを WARP の URL に書き換える。現在の実装は資料を URL で同定しており、`build_db.py` は本文（`texts.csv`）を URL で結び付けている。このままだと、リンクが WARP に変わった時点で次のことが起きる。

- 同じ資料が「削除」と「新規追加」に見える。
- 取得済みの本文が資料に結び付かなくなり、作り直した表から、その会議の場所・出席者が消える。

対応：

- `documents.csv` に `doc_key` 列を足す。WARP の URL（`https://warp.da.ndl.go.jp/info:ndljp/pid/<数字>/<元のホスト>/<元のパス>`）からは `<元のホスト>/<元のパス>` を、防衛省の URL からはホストとパスを取る。現在 `documents.csv` にある WARP の URL 1,616 件は、すべてこの形で、元のホストは www.mod.go.jp である（11/21 確認）。
- `build_db.py` が本文を結び付けるキーを、URL から `doc_key` に変える。
- 同じ `doc_key` のまま URL だけが変わった場合は、「WARP への移動」として記録する。
- 取得済みの PDF と本文は消さない。

### 3.6 PDF の原本

- 原本は、これまでどおり `raw/mod/files/` に置き、Git には入れない。現在の 421 件（約 350 MB）は、この端末にしかない。
- `fetch_files.py` は、手元にファイルがなければ取り直す作りになっている。まっさらな環境では毎回全件を取り直してしまうので、「台帳に SHA-256 があれば取得済み」に変える。手元にないものを取り直す場合は、明示のオプション（`--refetch-missing`）を使う。
- 原本は WARP に移った後、スクリプトでは取り直せない。保管先とバックアップは 8 節で決める。GitHub のランナーで動かす場合は、原本の保管先が決まるまで PDF の取得を本番にしない。

### 3.7 履歴とイベント

- `data/mod/events.csv`（追記のみ）：検知日時、イベントの種類、`council_id`、`meeting_id`、対象のキー、変更前、変更後、読み取り元のページ。
- `data/mod/members_history.csv`：名簿が変わったとき、変わる前の名簿を時点（`as_of`）付きで残す。`members.csv` は最新の名簿のままとする。
- イベントは、表の差分から機械的に作る。Gemini には作らせない。

### 3.8 回帰の検査

表を作り直した後、commit の前に次を確かめる。

- 前回の表にあって今回ない行を、表ごとに列挙する。
- 消えた行が、今回変更のあったページか、`doc_key` の変更で説明できること。説明できない行が 1 件でもあれば、commit せずに失敗にする。
- `build_db.py` の警告が前回より増えていれば、通知に載せる。

### 3.9 Gemini の役割

既存の読み取りを置き換えず、足りないところを補う。

| 用途 | 対象 | 出力先 |
|---|---|---|
| 画像だけの PDF の文字起こし | 現在 4 件と、今後の新規分 | `data/mod/text_llm/` と `texts.csv` の `note` |
| 出席者を読み取れなかった議事要旨・議事録の読み取り | 現在 20 件（185 件中）と、今後の新規分 | `data/mod/llm_extractions.csv`。検証を通ったものだけ、出所を付けて本体の表に反映 |
| 議事要旨・議事録・資料の要約 | 新しく取得した本文 | `data/mod/summaries.csv` |
| 変更の検討メモ（何が変わり、どこを確認すべきか） | イベントがあった日だけ | 通知（Issue）のコメント。表には入れない |

規則：

- 変更のないページ、処理済みの本文には呼ばない。本文の SHA-256 をキーにして、同じ入力を二度処理しない。
- `meeting_id`・`person_id` などの ID を Gemini に決めさせない。既存の規則で決める。
- 検証を通らない出力は捨てて、記録に残す。検証の例：
  - 抽出した氏名が、空白を除いた原文にそのまま存在する。
  - 開催日が日付として成り立つ。原文に曜日があれば一致する。
- 出力の各行に、モデル名、プロンプトの版、生成日時、入力の SHA-256 を残す。プロンプトはリポジトリに置く。
- モデルは設定で固定する。変えるときは評価（Phase 3）をやり直す。
- 1 回の実行での呼び出し数に上限を設ける（`--max-llm-calls`、既定は 20）。既存の 421 件をさかのぼって処理するのは、明示の指示があったときだけ。
- 渡すのは公開されている防衛省の資料だけ。API キーは環境変数（GitHub Secrets）から読み、ログに出さない。
- 要約と検討メモは機械生成であることを README に明記する。

### 3.10 通知と監視

- **変更があった日**：イベントの一覧を載せた Issue を作る。
- **失敗した日**：ジョブを失敗にする（GitHub からメールが届く）。
- **取り込み漏れの見張り**：RSS のジョブが、審議会ページの更新告知と台帳の取得日時を照合する。告知から 3 日たっても取り込まれていないページがあれば、Issue を作る。
- **生存確認**：HTML のチェックが 7 日以上成功していなければ、RSS のジョブが Issue を作る。セルフホストランナーなら Actions の実行履歴で判定する。タスクスケジューラの場合は、週 1 回だけ最終チェック日時を commit する。

### 3.11 Git の運用

- 定期実行は既定ブランチでしか動かない。現在の既定ブランチは `claude/wonderful-darwin-ke2hq0` なので、`main` を作って既定にするかを決める（8 節）。
- 自動の commit は、`git pull --rebase` の後に push する。同じワークフローが重ならないようにする（`concurrency`）。
- 権限は `contents: write` と `issues: write` に絞る。
- RSS のジョブが触るのは `data/mod/rss_items.csv` だけにして、もう一方のジョブと同じファイルを書かない。
- 実行時刻は、混み合う毎時 0 分を避ける。RSS は 19:37（JST。告知は 18〜19 時台に出る）、HTML のチェックは 07:17（JST）を初期値とする。

## 4. 制約

- 取得は直列で、2 秒以上の間隔をあける。並列にしない。
- User-Agent は、既存と同じく自己申告の名前にする。
- コマンドのオプション：`--dry-run`（書き込み・push・Gemini の呼び出しをしない）、`--no-llm`、`--council <council_id>`、`--limit <N>`、`--max-llm-calls <N>`。
- 止める規則は 3.4 節のとおり。
- この端末の Python は 3.14。ランナーでも同じテストが通ることを確かめる。

## 6. 実装の手順

各 Phase の終わりに、テスト結果と確認事項を報告する。

### Phase 0：前提の確定

1. `check_access.py` と `connectivity_check.yml` を作る。GitHub のランナーから、HTML（通常の取得と条件付き取得）、PDF、RSS に 1 件ずつアクセスし、ステータスと `cf-mitigated` ヘッダを記録する。
2. HTML が 403 なら、そこで結論とする。200 なら、7 日続けて定期実行し、安定して通るかを見る。
3. この端末でも同じスクリプトを数日動かし、Python での取得が続けて通るかを見る。
4. セルフホストランナーをこの端末に入れられるかを確かめる。
5. リポジトリの公開設定と既定ブランチを確かめる。
6. README のアクセス制約の表を、11/21 の実測に合わせて直す。

完了の条件：実行場所が決まっている。8 節の 1〜3 が決まっている。

### Phase 1：更新チェックと取り込み（Gemini なし）

1. 台帳に `content_sha256` を足し、既存の 123 ページ分を埋める。
2. `check_updates.py` を作る（3.2〜3.4 節）。
3. `doc_key` を入れ、`build_db.py` の結び付けを変える（3.5 節）。変更の前後で、既存の表の中身が変わらないことを確かめる。
4. `fetch_files.py` のスキップ条件を直す（3.6 節）。
5. `events.py` と回帰の検査を作る（3.7、3.8 節）。
6. `update.py` で日次の流れをつなぐ。
7. テストを足す。保存済みの HTML を使い、次の場合を確かめる：変更なし、本文の変更、差し込みスクリプトだけの違い、`Last-Modified` だけの違い、403 での停止、リンクの WARP への移動。

完了の条件（実地の確認）：

- 未反映の更新を取り込む。`kousei_nyusatu/index.html` が変更ありと判定される。
- `members.csv` に辻岡信也氏の行が加わり、名簿の時点が令和8年10月28日から11月20日に変わる。この 2 つがイベントとして記録される。
- それ以外の行が消えていない。
- 続けてもう一度実行すると、変更なしになる。

### Phase 2：定期実行と監視

1. `rss.yml` と `update.yml` を作る（タスクスケジューラの場合は登録の手順）。
2. 通知と見張りを作る（3.10 節）。
3. README に運用の手順を書く：止まったときの確認、ブラウザ経由への切り替え、手動での実行。
4. 1 週間動かして、誤検知と取りこぼしがないかを見る。

完了の条件：7 日間、変更のない日に commit が発生していない。変更のあった日に、イベントと通知が出ている。

### Phase 3：Gemini（評価してから限定して導入）

1. **評価**：出席者を読み取り済みの会議から 30 件を選ぶ（選び方は `make_check_sheet.py` と同じ）。本文を Gemini に渡して開催日時・場所・出席者を抽出させ、既存の表と比べる。食い違いは原文で判定する（既存の表の側が誤っている場合もある）。一致の割合と誤りの種類を報告する。
2. 本番に使う基準を決める（8 節）。
3. 3.9 節の 4 つの用途を、検証と出所の記録を付けて実装する。
4. `--max-llm-calls 5` で 1 会議体を処理し、出力を確かめてから定期実行に入れる。

完了の条件：評価の結果が報告され、基準を満たしている。検証を通らない出力が表に入らないことを、テストで確かめている。

## 7. 元の案からの変更点

| 元の案 | 修正版 | 理由 |
|---|---|---|
| 白紙から新しいシステムを作る（`src/mod_monitor/`、会議ごとの JSON） | 既存のスクリプトと CSV に足す | 既存の表・ID・検証済みの読み取りを生かす。別系統を作らない |
| GitHub のランナーで全処理 | RSS だけ GitHub のランナー。HTML は Phase 0 の結果で決める | 米国のデータセンターからの HTML は 403 だった |
| 403 なら Cloud Run（東京）に移す | この端末で実行する（セルフホストランナーかタスクスケジューラ） | 東京のデータセンターで通る保証がない。この端末からは取得できている |
| Playwright に差し替え可能にする | 採用しない | 静的な HTML で描画は不要。ボット検証の通過に当たる |
| URL ごとのハッシュで差分を検知 | 条件付き取得と、差し込みスクリプトを除いたハッシュ | 生のハッシュは取得のたびに変わる |
| 既知の URL かどうかで PDF を判定 | `doc_key` で同定し、週 1 回の照合で差し替えも検知 | WARP への移動と差し替えを扱えない |
| 全エラーに最大 3 回リトライ | 403・429 は即停止。リトライはタイムアウトと 5xx だけ | 既存の方針 |
| HTML と PDF の抽出を Gemini で行う | 既存の読み取りを使い、Gemini は補完と要約に限る | 既存の処理で 123 ページを読めている。出所と検証が要る |
| pypdf / pdfplumber | pdfminer.six のまま | 本文が変わると、出席者の読み取りに影響する |
| PDF は一時領域に落として捨てる | 原本を保管する | WARP に移った後は取り直せない |
| 名簿は最新だけを保存 | 履歴とイベントを残す | 変更の経過が研究上の情報になる |
| 日次のサマリーを Markdown で commit | イベントの表と Issue | 機械可読の記録と通知を兼ねる |
| RSS は対象外 | 対象にする | 開催告知は RSS にしか出ないものがある。取り込み漏れの見張りにも使える |
| アーカイブ区分は任意 | 既定で対象 | 更新があり、条件付き取得なら負荷は小さい |
| 初回のベースライン構築 | 不要 | 11/19 時点のデータベースがある |

元の案から引き継いだもの：疎通の確認を最初に行う、直列で間隔をあける、User-Agent を明示する、WARP と外部サイトを巡回しない、変更分だけ Gemini に渡す、`--dry-run` などの安全装置、API キーを Secrets で扱う、PDF を Git に入れない。
